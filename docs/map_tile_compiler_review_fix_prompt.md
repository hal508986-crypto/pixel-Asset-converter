## 必須修正1: 非接続辺・接続幅・四隅を正しく検証

`acceptance.py::_validate_mask` は、非接続辺の中央ウィンドウを検査対象から外し、接続辺では許可窓の外への漏れを拒否していません。

査読の負例では、正しいNS道路に東向きの枝を加えても、幅を15pxから31pxへ広げてもacceptedになりました。

- 非接続辺は中央と端点を含む辺全体で、禁止された道路の出現を検査する。
- 接続辺は許可窓の充足だけでなく、許可窓外への漏れ、位置ずれ、幅超過を検査する。
- `_edge_body` で除外している四隅も検証する。四隅を除外したまま検証済みと扱わない。
- 入力解像度と最終64pxでの幅の丸めを定義し、既存の有効な正例を不用意に拒否しない。許容値を使うなら、その根拠・単位・適用範囲を記録する。
- 色から前景を推定できない場合に、空マスク等を根拠に合格にしない。観測不能は未検証として扱う。

## 必須修正2: 完成PNGの内部連結性を検証

NS道路の中央6行を背景色で消しても、両端が残るためacceptedになります。

- 宣言された接続端が、完成PNGで同じ連結成分につながることを確認する。
- 使用する4近傍／8近傍等の規約を明示し、正常な曲線と分岐で妥当性を確認する。
- NS/EW、曲線、端点、T字について正例と負例を用意する。孤立した断片や別の道路片を、端点が存在するだけで正しい接続とみなさない。
- 入力マスクが正しくても、完成PNGが断線した場合は拒否する。
- 二値マスクだけの合格を、画像内で道路が維持されたことの代替にしない。前景推定の限界は検証状態に反映する。

## 必須修正3: surfaceの共有辺契約を採用判定へ接続

現在のsurface分岐はPNG整合性だけで合格し、`spec.shared_edge_contract` がゲートに渡されていません。緑と黄色の単色タイルを交互に割り当てた負例も全体acceptedでした。

- 既存Specの共有辺契約をコンパイル時と保存後の再検証へ渡す。
- 許可される隣接ペアと方向を定義し、最終PNGの対応辺・四隅を検証する。並べ替え可能な共有辺セットなら、元シートで隣り合っている組だけで済ませない。
- PNG整合性、接続整合性、美観レビューを分離する。必須の接続が未検証なら全体acceptedにしない。
- 「same base」等の文章だけから数値の厳密一致を勝手に仮定しない。既存契約で検証可能な条件と、機械可読な情報が不足する条件を分ける。後者は明示的な未検証にする。
- 厳密な画素一致と、見た目の連続性評価を区別する。辺の平均色だけで局所破損を見逃さない。
- 既存API・保存形式との互換性を考慮する。追加の検証設定が必要なら既存契約の利用案と最小拡張案を比較し、採った案と移行方針を記録する。
- 採用判定を通すためにタイル端を同色で塗る、しきい値を緩める、契約を削る、といった対応はしない。

## テストの進め方

まず査読の4負例を実行し、現在の状態を確認してください。

```powershell
py -3.10 e2e/map_tile_review_trial_20260907/reproduce_review.py
```

このスクリプトは観測用で、assertによる回帰テストではありません。4件の期待値をrejectedとするテストを先に追加し、Redを確認してから修正してください。既に修正済みなら再現不能の理由と差分を示し、残る不足に進んでください。

- 余分な東接続 → rejected
- 幅超過したNS道路 → rejected
- 中央が断線した道路 → rejected
- 共有辺が不適合なsurface群 → rejected（契約情報不足の場合は未検証を明示し、全体acceptedにしない）

負例だけをすべて拒否する実装にせず、有効な道と共有辺セットが合格する正例を必ず用意してください。四隅、曲線・端点・T字、入力が正常で出力のみ破損、比較ペア不足も確認してください。

コンパイル直後・`validate_asset_package`による再検証・CLIの判定を一貫させてください。必須契約がrejectedまたはunverifiedなら、検査用出力を残しても採用可能として成功扱いしないこと。provisionalのまま維持し、自動美観承認は行わないでください。

関連テストと既存機能の回帰を実行してください。前回は99 passedでしたが、今回の実行結果を新たに報告すること。
