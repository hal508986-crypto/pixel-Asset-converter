# Canvasサイズとpalette上限の比較検証（結論）

[Canvas拡張仕様](spec/canvas_scale_and_palette_budget_spec.md) のP2にあたる実素材検証の記録。
「出力Canvasをどこまで上げる価値があるか」「24色→36色は自然か」に答える。

## 0. 結論（先に）

1. **出力Canvasサイズは、元絵の見かけの格子で決まる。** 格子より大きいCanvasにしても、
   小さいCanvasを拡大したものとほとんど変わらない。
2. **palette上限は、元絵の可視色数で決まる。** 元絵にない色は増えない。24→36が意味を持つのは
   元絵が36色以上ある場合だけ。
3. **サイズを上げると1ドットあたりの情報密度は必ず下がる。palette上限でもdetail_levelでも
   補償できない。** これは避けられないので、密度を保ちたいなら元絵側を変えるしかない。
4. **減色と縮小ではドット絵は作れない。** 普通の絵も実写も、平坦面も1ドットの描き込みも
   持たない中間帯に落ちる（5節）。本ツールはドット絵素材の規格化が本旨で、
   普通の絵からは「色数を絞った縮小版」が得られるだけ。
5. **ただし合格ラインは用途で変わる。** 同じ中間帯の出力でも、背景・遠景など
   1ドットの意図を問われない役割なら実用品として通る（5.4）。実写512×341/48色が
   その例。スプライトとしては通らない。指標では測れない差なので目視で決めること。

### 推奨

| 元絵の見かけの格子 | 推奨する出力Canvas | 根拠（3節） |
|---|---|---|
| 32以下 | 64×64 | 128にしても19.7%しか変わらない |
| 64 | 128×128まで | 128で43.2%変わるが、256では24.4%に落ちる |
| 128以上／連続階調 | 256×256まで有効 | 256でも95〜100%変わる |

| 元絵の可視色数 | 推奨するpalette上限 |
|---|---|
| 上限より少ない | 元絵の色数に合わせる。上げても実測色数は増えない |
| 36以上 | 36〜48。密度がわずかに上がる（+0.02〜0.06） |

**detail_level は密度調整の手段にならない。** `sparse` と `balanced` は実質同一で、
`detailed` だけが少し上がる。既定の `balanced` を変える理由は見つからなかった。

## 3. 実験2: detail_level は密度に効くか（RC-02）

palette=24固定。`edge_color_changes` の sparse / balanced / detailed。

| 素材 | Canvas | sparse | balanced | detailed | 効き幅 |
|---|---|---|---|---|---|
| 格子32 | 64×64 | 0.337 | 0.340 | 0.343 | 0.006 |
| 格子32 | 256×256 | 0.078 | 0.079 | 0.079 | 0.001 |
| 格子64 | 64×64 | 0.718 | 0.718 | 0.785 | 0.067 |
| 格子64 | 256×256 | 0.183 | 0.182 | 0.199 | 0.016 |
| 格子128 | 64×64 | 0.768 | 0.769 | 0.839 | 0.071 |
| 格子128 | 256×256 | 0.351 | 0.351 | 0.396 | 0.045 |
| 連続階調 | 64×64 | 0.745 | 0.747 | 0.828 | 0.083 |
| 連続階調 | 256×256 | 0.519 | 0.519 | 0.613 | 0.094 |

比較対象として、同じ素材でCanvasを64→256にしたときの効き幅（palette24）:

| 素材 | 64×64 | 256×256 | 効き幅 |
|---|---|---|---|
| 格子32 | 0.340 | 0.079 | 0.262 |
| 格子64 | 0.718 | 0.182 | 0.536 |
| 格子128 | 0.769 | 0.351 | 0.418 |
| 連続階調 | 0.747 | 0.519 | 0.228 |

**RC-02の答え: detail_level は密度の補償手段にならない。**
効き幅は0.001〜0.094で、サイズの効き幅（0.228〜0.536）の3分の1から100分の1。
`sparse` と `balanced` の差は0.000〜0.003で実質同一。仕様2.4節で立てた仮説は否定された。

## 4. 実験3: 大きいCanvasに価値があるか（決定的）

密度指標は常に小さいCanvasを有利にするため、サイズ選択の判断には使えない。
「そのサイズにする価値があるか」は、**nativeで出したものが、小さいCanvasを拡大したものと
どれだけ違うか**で測る。差が小さければ、そのサイズは拡大しているだけで情報が増えていない。

`max_canvas_changed_visible_ratio_vs_upscaled_min`（palette24）:

| 元絵の格子 | 64→128 の差 | 128→256 の差 |
|---|---|---|
| 32 | 19.7% | 13.8% |
| 64 | 43.2% | 24.4% |
| 128 | 96.9% | 95.5% |
| 連続階調 | 100.0% | 100.0% |

**元絵の見かけの格子が、有効な出力Canvasサイズを決める。**
格子32の素材を128にしても2割しか変わらず、8割は拡大したのと同じ。
一方で格子128以上や連続階調の素材は、256でも95%以上が変わるので、256にする価値がある。

これが0節の推奨表の根拠。

## 5. 実験4: 普通の絵を通すとどうなるか（ストレステスト）

本ツールはドット絵素材（Asset）の規格化を旨とするが、**格子を持たない普通の絵を
通すとどうなるか**を確認した。想定用途ではなく、限界を知るためのストレステスト。
連続階調のイラスト1枚（5.2）と、実写写真1枚（5.3）を通している。

### 5.1 指標

- **ドット変化率**: 上下左右の4近傍すべてと色が異なる画素の割合。
  高いほど1ドット単位で色が置かれている。
- **水平ラン平均**: 同じ色が横に続く長さの平均。高いほど平坦な面がある。
- **硬い輪郭率**: 隣接ドット間のRGB差が90以上の箇所の割合。輪郭が立ったまま残っているか。

**水平ラン平均は単独で読まない。** 縮小率が大きいと、bicubic平均が強く効いて隣接画素が
同じpaletteへ落ち、平坦面ではなく**ボケ由来の長いラン**が出る（5.3で実際に逆転した）。
ラン長は硬い輪郭率とセットで読むこと。

### 5.2 イラストを通す（縮小2.7倍）

素材は連続階調のイラスト1枚（1122×1402 / 可視338,860色 / 格子なし）。
出力は410×512 / palette上限49色、輪郭あり。

| | 色数 | ドット変化率 | 水平ラン平均 |
|---|---|---|---|
| 真のドット絵 格子32 | 7 | 29.9% | 3.73px |
| 真のドット絵 格子64 | 21 | 48.2% | 4.73px |
| 真のドット絵 格子128 | 62 | 54.8% | 6.48px |
| **普通の絵を通した出力** | 49 | **15.3%** | **2.59px** |
| 参考: 素朴な縮小＋減色（同49色） | 49 | 22.3% | 1.93px |
| 参考: 最近傍縮小のみ（減色なし） | 42,819 | 0.0% | 1.64px |

**真のドット絵は「広い平坦面」と「1ドット単位の描き込み」を両方持つ。**
ラン長も変化率も高い。一方、普通の絵を通した出力は**どちらも低い中間帯**に落ちる。
なめらかでもなく、ドットも立っていない。

ただし**コンパイラは素朴な縮小より確実に良い**。同じ49色でも、平坦面が34%長く
（1.93→2.59px）、ちらつきが31%少ない（22.3%→15.3%）。単なる劣化ではない。

同じ素材をサイズ違いで通すと、**読めるかどうかを決めているのは色数ではなく解像度**だった。

| 出力 | 総ドット数 | 実測色数 | ドット変化率 | 水平ラン平均 |
|---|---|---|---|---|
| 102×128 / 24色 | 13,056 | 24 | **22.7%** | **1.92px** |
| 205×256 / 24色 | 52,480 | 24 | 15.9% | 2.39px |
| 410×512 / 49色 | 209,920 | 49 | 15.3% | 2.59px |

102×128の数値は「素朴な縮小＋減色」（22.3% / 1.93px）とほぼ完全に一致する。
**このサイズではコンパイラの整えが素朴な縮小と区別できなくなる。** 目視でも顔の構造が失われ、
被写体が読めない。一方205×256は24色でも410×512とほぼ同じ帯にいる。

見た目が破綻しないのは**ドット数の多さによる**。この解像度なら「ドット絵」ではなく
「色数を絞った精細なイラスト」として読める。逆に小さいCanvasへ落とすほど、
1ドットあたりの意図の有無が露呈する。これは4節の結論（元絵の格子が有効サイズを決める）と同じ話。

なお本素材は`格子なし`のため4節のルール（元絵の格子が有効サイズを決める）は効かず、
代わりに**被写体のディテールが何ドットに収まるか**が下限を決めていた。

### 5.3 実写を通す（縮小12.3倍）

素材は写真1枚（6299×4199 / 3:2 / 可視575,933色 / 格子なし）。被写体は港に係留された漁船。
出力は512×341 / palette上限48色。

| 出力 512×341 | 実測色数 | ドット変化率 | 水平ラン平均 | 2×2平坦ブロック率 | 硬い輪郭率 |
|---|---|---|---|---|---|
| **コンパイル結果** | 48 | **17.3%** | **2.44px** | 34.8% | **6.23%** |
| 参考: 素朴な縮小＋減色 | 48 | 11.0% | 2.96px | 37.1% | 0.43% |
| 参考: 最近傍縮小のみ | 44,633 | 0.0% | 2.10px | — | — |
| 対照: イラスト410×512（5.2） | 49 | 15.3% | 2.59px | 43.1% | 6.95% |

**指標上、実写とイラストはほぼ同じ帯にいる。** パイプラインが実写を特別扱いしているわけではない。

コンパイラの寄与は硬い輪郭率にはっきり出る（0.43% → 6.23%、14倍）。索具のワイヤー・マスト・
手すり・船体のウォーターラインが1ドット幅の線として残り、素朴な縮小では灰色のにじみに溶ける。

ここで**ラン長が逆転する**。実写では素朴な縮小のほうがラン長が長い（2.96px > 2.44px）が、
これは平坦面ではなくボケである。硬い輪郭率0.43%がそれを示している。5.1の注記のとおり、
ラン長だけを見ると結論を誤る。

### 5.4 読み取れること

**減色と縮小ではドット絵は作れない。** ドット絵の本質は「どのドットに何色を置くか」という
離散的な判断で、連続階調の絵にはその判断が含まれていない。これは実装の問題ではなく
情報の問題であり、パイプラインの改良では埋まらない。

**ただし、合格ラインは用途で変わる。** 実写の出力（512×341 / 48色）は指標上イラストと
同じ中間帯にいるのに、見た目は実用品として通る。差は絵の側ではなく**期待の側**にある。
512×341 / 48色という規格は90年代の背景アセットそのもので、背景は当時から
「限られた色数で描いた絵」であり、1ドットずつ意図を置いた絵ではなかった。
**「絵っぽさ」が減点にならない用途がある。** 逆にキャラクタースプライトは1ドット単位の
意図が問われるため、まったく同じ品質の出力が甘いと読まれる。

これは指標では測れない。**同じ数値でも、役割が変われば採否が変わる**という限界として扱う。

### 5.5 位置づけ

| 入力 | 得られるもの | 向く用途 |
|---|---|---|
| ドット絵素材 | 格子を保ったままの規格化 | 本来の用途。スプライト・タイルすべて |
| 普通の絵・実写 | 色数を絞った縮小版。ドット絵ではない | 背景・遠景など、1ドットの意図を問われない役割なら実用 |

後者を「ピクセルアート化」と呼ぶと期待とずれる。GUIには元絵の格子情報が出るので
（`格子なし` と表示される）、利用者はその場で判別できる。

## 6. この検証の限界

結論を使うときに、次を承知しておくこと。

- **4素材のみ。** いずれも縦長の立ち絵で、同一の生成モデル由来。横長被写体・小物・
  細線主体などでは傾向が変わる可能性がある。
- **構図は「被写体を収める」のみ。** 「画面全体をそのまま使う」構図では被写体の拡大率が
  変わるため、密度の絶対値は異なる。傾向（サイズを上げると密度が下がる）は変わらないはず
  だが未検証。
- **指標は `edge_color_changes` と対照比較の2つのみ。** 見た目の良し悪しそのものは測っていない。
  最終的な採否は目視で決めること。
- 格子32の素材は元絵の色数が7色しかなく、格子と色数を分離できていない。
  格子が粗いのか色数が少ないのかを分けるには、格子32で色数の多い素材が要る。
- 5節のストレステストは**イラスト1枚と実写1枚のみ**。絵柄・被写体・解像度で傾向が変わる
  可能性がある。特に実写は「硬い輪郭を持つ人工物が主被写体」という有利な条件だった。
  人物や植物のような柔らかい被写体では輪郭が残らず、結果が変わるはず。
- **5.4の「用途で合格ラインが変わる」は指標の裏づけがない。** 目視の判断であり、
  この検証の他の結論とは根拠の強さが違う。

## 8. 再現方法

実験1・2は `CanvasScaleStudyRunner` を素材ごとに回す。設定は素材のパスだけ差し替える。

```python
from pathlib import Path
from pixel_tile_compiler.character_study.canvas_scale import (
    CanvasScaleStudyConfig, CanvasScaleStudyRunner,
)

config = CanvasScaleStudyConfig(
    source=Path("G:/マイドライブ/.../study_assets/03_portrait_grid64_palette24.png"),
    output_root=Path("e2e/canvas_scale_study_20260909/03_portrait_grid64_palette24"),
    canvas_sizes=((64, 64), (128, 128), (256, 256)),
    palette_budgets=(16, 24, 36, 48),
    detail_levels=("balanced",),          # 実験2では ("sparse","balanced","detailed")
)
result = CanvasScaleStudyRunner().run(config)
print(result.metrics_path, result.sheet_path)
```

実験3（大きいCanvasに価値があるか）は `NativeResolutionStudyRunner` を2サイズずつで回し、
`metrics/resolution_metrics.json` の `max_canvas_changed_visible_ratio_vs_upscaled_min` を読む。

```python
from pixel_tile_compiler.character_study.native_resolution import (
    NativeResolutionStudyConfig, NativeResolutionStudyRunner,
)

config = NativeResolutionStudyConfig(
    source=Path(".../05_portrait_grid128_palette64.png"),
    output_root=Path("e2e/canvas_scale_study_20260909/native_pairs/05_128_256"),
    canvas_sizes=((128, 128), (256, 256)),
    palette_budget=24,
)
```

出力はいずれも `e2e/` 配下でGit管理外。素材が増えたら同じ手順で回し、本書の表を更新する。

**5節（実験4）はランナーを持たない。** ドット変化率・水平ラン平均・硬い輪郭率は
コンパイル結果のPNGを直接読むアドホック計測で、リポジトリのAPIではない。定義は5.1節にあり、
いずれも数行で書ける。`2×2平坦ブロック率` だけは実装があり、
`character_study.canvas_scale._two_by_two_uniform_block_ratio` を使った。
比較対象の `baseline_bicubic_quantized.png` / `baseline_nearest.png` は
コンパイルのたびに出力フォルダへ常に書かれる（`pipeline/compiler.py`）。設定は要らない。
